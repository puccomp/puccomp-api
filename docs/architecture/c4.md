# Arquitetura — C4 Model

O [C4 Model](https://c4model.com/) é a nossa lente de referência para descrever a
arquitetura em quatro níveis: **contexto**, **contêineres**, **componentes** e
código.

## Estado atual

Por ora **não mantemos diagramas C4 desenhados à mão**. O custo de manter um
diagrama sincronizado com o código não se paga neste estágio do projeto — e a
fronteira entre módulos, que é o que mais importa, já é **garantida pelo build**,
não por diagrama: `ModularityTests.verifiesModuleBoundaries()` quebra o build se
um módulo acessar o interno de outro (ver
[ADR 0001](../adr/0001-monolito-modular-com-spring-modulith.md)).

Os **Níveis 1 e 2** (contexto e contêineres — atores, banco, SMTP,
observabilidade) ficam para quando o sistema estabilizar e o desenho valer a
manutenção.

## Nível 3 (componentes) — gerado pelo Spring Modulith

O Spring Modulith gera a visão de componentes automaticamente a partir do código,
sem precisar desenhar nada. Rodar o teste:

```bash
./gradlew test --tests "*ModularityTests"
```

escreve em `build/spring-modulith-docs/` (efêmero, ignorado pelo git):

- **Diagramas** (`components.puml`, `module-*.puml`) — em notação **C4-PlantUML**,
  com os módulos como `Component` e suas dependências. Cobrem apenas o Nível 3.
  Como são PlantUML, **não renderizam direto no GitHub** — precisam de um
  renderizador PlantUML; servem como cross-check on-demand, não como artefato
  versionado.
- **Module canvas** (`module-*.adoc`) — uma ficha por módulo com a descrição (puxada
  do `package-info.java`), o pacote base e os componentes/serviços que o módulo
  expõe. É a melhor referência de metadados de cada módulo, e vem sempre fiel ao
  código.

Para uma leitura rápida da organização dos módulos sem gerar nada, veja a seção
**Arquitetura** do [CONTRIBUTING.md](../../CONTRIBUTING.md#arquitetura).
